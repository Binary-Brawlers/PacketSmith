# ADR-0004: Role of SQLite as Derived Cache and Index

- **Status:** Accepted
- **Date:** 2026-09-04
- **Authors:** PacketSmith Architecture Team

---

## Context and Problem Statement

PacketSmith requires high-throughput search, quick indexing over thousands of requests, detailed execution history, response payload caching, and workbench layout restoration. We need to decide where this state lives without violating the Git-friendly, open-format principle.

## Considered Options

1. **Store everything in SQLite:** Violates Git-friendliness for user-authored requests.
2. **Store everything in flat files:** Makes full-text search, history filtering, and sorting extremely slow on large workspaces.
3. **Hybrid Architecture:** Human-authored resources live in versioned flat files; SQLite is used strictly as an ephemeral, rebuildable local cache (`.packetsmith/cache.db`).

## Decision Outcome

Chosen option: **Hybrid Architecture with SQLite as derived cache and index.**

### Positive Consequences
- If `.packetsmith/cache.db` is deleted or corrupted, it can be completely regenerated by re-scanning the workspace files.
- `.packetsmith/cache.db` is added to `.gitignore`, preventing binary database churn in Git repositories.
- Fast sub-millisecond full-text search, history queries, and tab layout restoration.
- Supports WAL mode and robust concurrent reads without UI freezing.

### Negative Consequences
- Need to maintain indexing and cache invalidation logic as files change on disk.
